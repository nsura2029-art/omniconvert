# Components DOX

## Purpose
- Owns the React UI components for navigation, auth, conversion workflow, dashboard, billing, admin, onboarding, hero selector, and workflow builder.

## Ownership
- `ConversionPanel.tsx` owns upload sources, drag/drop, conversion simulation, progress logs, generated outputs, and related dialogs.
- `AuthModal.tsx` owns sandbox sign-in/sign-up and social-login simulation.
- `Dashboard.tsx`, `Billing.tsx`, and `AdminDashboard.tsx` own localStorage-backed product/account/admin surfaces.
- `Navbar.tsx` owns navigation, the Tools/All Tools header menu, theme toggle, user menu, and credit indicators.
- `CategoryPage.tsx` owns dynamic category converter landing pages, category-specific bento matching, supported-format summaries, FAQs, and category-only tool grids.

## Local Contracts
- Auth is currently simulated in the client; do not present it as production authentication.
- Admin/user/conversion/referral data currently comes from browser `localStorage`.
- Cloud upload sources are mock pickers unless a future backend integration is added.
- Upload UX should use the inline icon/button source selector before deeper URL/cloud picker modals; avoid falling back to native select menus for choose-file source picking.
- CAD seed fixtures under `public/seed-files/cad/` are for URL/manual browser QA. Do not show a production-facing "Try sample file" button unless explicitly requested.
- The Tools/All Tools header menu should follow the Convertio-style category menu pattern: category entries link to dedicated dynamic category pages instead of simply scrolling users to the generic tools directory. CAD should be promoted as a first-class category because it is not a common default browsing path.

## Work Guidance
- Keep component edits behavior-preserving unless the user explicitly asks for product logic changes.
- Avoid layout churn in established panels; prefer targeted control/state updates.
- Category pages should be dynamically populated from category/tool data, SEO-friendly, and show a category home experience with a bento grid matcher plus only that category's supported source and target formats.
- Approved category-card visual systems from `design-mockups/card-systems-5.html` are 3D Tilt Conversion Cards for featured/high-intent routes, Format Rail Cards for explicit source-target education, and Dense Utility Cards for large route grids.
- CAD category tool grids should use Dense Utility Cards: compact clickable cards, no visible credit labels, clear mouseover affordance, and light arrow surfaces instead of dark arrow pills.
- CAD detail pages should place Related CAD converters directly below the upload/converter section, showing up to 6 related tools in a 2-row grid plus a Browse all CAD tools link. Cross-category popular tools belong in a separate Popular tools section grouped by 3 categories with 3 tools each.
- Programmatic SEO category/detail page UI must preserve unique H1/body copy, related links, FAQs, and route-specific limitations from the SEO data model.
- Informational pages such as Security must align with category-page rhythm: use comparable H1/body/section heading sizes, keep breadcrumb-to-heading spacing compact, keep breadcrumbs left-aligned and sticky, and maintain section gaps consistent with `CategoryPage.tsx` rather than landing-page hero spacing.
- Use lucide-react icons already imported or add icons from lucide-react when needed.
- Match the Format OS light palette and avoid reintroducing purple-heavy gradients as the dominant visual language.
- In `ConversionPanel.tsx`, the bundled **Download all** action (next to **Clear all** in the CAD converter shell) zips every converted output into `omniconvert-conversions-YYYY-MM-DD.zip` via the inline `buildZip` STORE writer. Do not introduce a third-party ZIP dependency unless the writer's scope grows beyond the current single-bundle download. The button's `disabled` state must be gated on a `canDownload` derivation that requires BOTH `allConverted` AND a non-empty `conversions` array — `allConverted` alone (derived from `pendingCount` + `lastConvertedTargets`) can briefly report true while `conversions` is still being repopulated by `handleConvert` after the Convert-all-to flow, which made the button look enabled but silently do nothing. The handler also flashes a `cadNotice` when invoked with an empty conversions array so the user gets feedback instead of a dead click.
- Primary action buttons that drive a single conversion (CAD **Convert** button, **Initiate Sandbox Convert**) must reuse the `btn-primary` mesh-gradient token so they match the navbar `Sign In` button.
- The **Convert** action in `ConversionPanel.tsx` must only process files whose current entry in `fileProgresses` is missing or not `completed`. Already-converted files are skipped, their progress is preserved, and conversions from prior runs are merged into `conversions` rather than replaced. Creator tools (TTS, Markdown to HTML) keep their virtual-file fallback when `files` is empty. `handleConvert` accepts an optional `forceAll` flag used by `applyCadConvertAll` to force a fresh pass; do not reset `conversions` or `fileProgresses` inside `handleConvert` itself — that reset belongs in explicit user actions (Clear all, tool change) or in callers that opt into a forced pass.
- The conversion pipeline runs each file **in parallel** via `Promise.all(itemsToConvert.map(processSingleFile))`. Per-file state (progress, logs, conversion record) is kept independent through closures; do not reintroduce a sequential `for...await` loop.
- The CAD pipeline has a **real browser-side fallback** for the small text-based mesh subset where conversion is lossless without an engine: STL<->OBJ and OBJ<->PLY. Implemented in `tryRealCadConversion` (file-level helper) and exercised by the parser/serializer functions (`parseAsciiStl` / `writeAsciiStl` / `parseObj` / `writeObj` / `parsePly` / `writePlyAscii` / `stlToObj` / `objToStl` / `objToPly` / `plyToObj`). Any other CAD pair (DWG/DXF/STEP/IGES/IFC/SKP/...) stays on the simulated placeholder until a server engine is wired. Do not claim browser-feasibility for those pairs in UI copy or in `CAD_TARGET_MATRIX` without doing the work.
- Seed fixtures for the real converters live in `public/seed-files/cad/` — `sample-stl-cube.stl` and `sample-obj-cube-unit.obj` are both 12-triangle unit cubes (centered at origin, side=1) used to smoke-test the round-trip. Do not replace them with proprietary or non-synthetic geometry.
- A file whose TO has been changed via the picker (or via `applyCadConvertAll`) must be re-processed on the next Convert click even if its previous run completed. The conversion state tracks `lastConvertedTargets[fileName]` so the filter can compare current target vs last-used target; both are cleared by Clear all, tool change, and on per-file remove.
- `applyCadConvertAll(format)` MUST pass the newly-computed `nextTargets` to `handleConvert` via the `overrideTargets` parameter (it calls `handleConvert(true, nextTargets)`). Without this override, `handleConvert` runs in the same render as `setTargetFormats(nextTargets)`, so its closure-captured `targetFormats` still holds the OLD values — the resulting conversion record is written against the old format and `lastConvertedTargets` is set against the old format too, leaving the row showing a mismatched chip + filename and `pendingCount > 0` in the next render. The same override path also applies to the per-file `TargetFormatPicker` flow where the user changes the TO and clicks Convert in a later render (no override needed there because the next render's closure is fresh).
- The per-row **Target format** selector uses the inline `TargetFormatPicker` component (search + category list + format chips, click-outside and Escape to close). Categories are derived from `FORMAT_CATEGORY_MAP`, which covers every writable format from `docs/fonts/cloudconvert_format_catalog.json` and maps to all 12 platform categories: Documents, Spreadsheets, Presentations, Images, Audio, Video, Archives, CAD, eBooks, Vectors, Fonts, 3D Models. `CAD_TARGET_MATRIX[sourceExt]` provides a cross-category target list per source extension so that loading any CAD source surfaces every reachable category in the picker (not just CAD). Categories a CAD source cannot reach (e.g. Audio / Video / Fonts) simply don't render because no formats in the source's target list map to those categories. Many of the cross-category targets are NOT browser-feasible (DWG → PDF, STEP → DOCX, etc.) — they fall through to the simulated placeholder when the user clicks Convert. The picker's two-column layout (categories left, format chips right) is sized at `max-h-[360px]` to accommodate the larger category list, and the left category column scrolls internally so the picker height stays bounded. The picker is **light-themed** (white / slate-50 surfaces, dark text, blue accent on active category and selected chip); do not return to a dark zinc-950 surface without updating the DOX. Do not replace this picker with a native `<select>` or introduce a third-party dropdown/menu library without updating the DOX contract.
- Each file row renders a **type-specific colored icon chip** for both the input file and the converted output. The mapping lives in `FILE_TYPE_TABLE` and is keyed by extension (Image=pink / Audio=violet / Video=rose / PDF=red / DOC/DOCX=blue / Sheets=emerald / Text=slate / Markup=orange / Code=amber / Ebook=indigo / Archive=yellow / 3D/CAD=orange / fallback=neutral). The converted-output icon gets a small green ✓ badge in the bottom-right corner to keep the success signal. Do not collapse back to a single generic File icon for all rows without updating the DOX.
- The per-row progress indicator is a **single-fill, left-to-right progress bar** (`SingleProgressBar`) positioned directly below the input filename and extension chip — not in its own grid column. Width is animated via **plain CSS transition** (`transition: width 200ms ease-out`) on a plain `<div>` (no `motion/react`, no dual fills). The bar is a slate-100 track with a solid `bg-blue-500` fill at `width: ${value}%` — no gradient meeting point to jitter, no overlapping fills to fight. When the file is already converted, the entire progress strip swaps to a static inline "100% Complete" indicator (CheckCircle + label) so the eye doesn't group it with live, animating bars. When `value === 100`, the fill is also `opacity: 0` as a fallback safety net even if the parent forgot to swap. The older `UploadProgressBar` (dual-anchored) is retained as a dead helper for now — do not reintroduce it as the per-row indicator, do not change SingleProgressBar to use a gradient, and do not wrap it in `motion/react` without updating this contract.
- The `UploadZone` shell is a **plain white browser background** (no rounded card, no dashed border, no grid pattern, no animated tint). The Phase 1 strip removed every "card" affordance from the entire Choose Files flow so the page chrome is the browser's own white surface. The only visual change on drag-over is `bg-blue-50/40` via a static class swap. Future contributors cannot reintroduce the rounded-card / dashed-border / grid pattern style without breaking the contract.
- Files that have already been converted must render a **static** "Done" pill (green check + "100%") in the progress column instead of the animated `UploadProgressBar`. The animated bar is reserved for files that are currently being processed or are pending / analyzing. This prevents already-converted rows from looking like they're reprocessing when the user adds a new file and clicks Convert.
- Each `UploadedFileRow` always renders a **paired output row** underneath its input row, regardless of whether the file has been converted. Layout: file info on the left (flex-1) — icon + filename + target-format chip + size; **Download button right-aligned in the SAME row** — only rendered when the file is converted. The output row has NO eyebrow label ("Converted output" / "Awaiting conversion") — the input row's status line already reads "Ready to download · ✓ 100% Complete" inline (single horizontal line) so the duplicate label on the output row was redundant. When pending, the output row shows a dashed-border, slate-tinted placeholder with the projected filename + ghost target chip; when converted, the same grid cells swap to the green view with the real conversion filename + size + Download button. The surrounding box (padding + border + bg + border radius) is byte-identical between the two states so conversions complete without shifting the file list or the sticky action row — this eliminates the layout-shift flicker that used to happen on single-file completion. The gradient divider below the output row is also unconditional for the same reason. Row keys are content-derived (`${file.name}-${file.size}-${file.lastModified}`) so removing a middle row never remounts the rows below it. Do not reintroduce conditional rendering of the output row, the divider, the index-based key, wrap the Download button onto a separate line, or add back the "Converted output" / "Awaiting conversion" eyebrow.
- The input row's progress / status strip is a single horizontal line. When idle, it renders the `SingleProgressBar`. When converted, it renders `✓ 100% Complete` + a thin vertical divider + `Ready to download` inline (no separate vertical stack). The `statusText` (`Ready to convert` / `Analyzing file...` / `Ready to download`) lives ABOVE this strip on the second text line under the filename, so the converted row reads top-to-bottom as: filename + extension chip → `Ready to download` → `✓ 100% Complete | Ready to download` (the second "Ready to download" is redundant on purpose — it surfaces the same info in two visual planes so a user skimming the row can't miss it). Do not split the converted indicator onto its own row or hide the `statusText` when converted.
- When the **first file is uploaded**, the workspace appears below the fold on most viewports (the upload placeholder sits below the page intro). A `useEffect` watches `files.length` and scrolls `#cad-conversion-workspace` into view with `block: 'end'` on the 0→1 transition, so the convert row lands in the browser visible area without the user having to scroll manually. Subsequent adds (1→2, 2→3, ...) do NOT scroll — the workspace is already in view, and yanking the page on every add would be jarring. The ref pattern (previousFileCountRef) is used instead of a plain comparison because the dep array is `files.length`, not `files`.
- Changing the global **Convert all to** dropdown (`applyCadConvertAll`) must update `targetFormats` for every file AND re-run `handleConvert(true)` so each row shows a fresh converted-output card with the new format. Prior `conversions` are cleared at the start of that forced pass so rows never carry a stale result.
- The CAD shell action area below the file list is structured as **a single horizontal action row** (Phase 1 cleanup) split into a left cluster and a right cluster pushed by `ml-auto`: Left cluster: `Convert all to` bulk select → status counter (`X of Y converted · N pending`) → `Clear all`. Right cluster: `Convert` (btn-primary, label is just "Convert" / "Converting..." — the count is already conveyed by the status counter so the button stays a fixed-width CTA) → `+ Add more files` (opens native file picker directly) → `Download all`. There are no popovers, no save-destination chooser, no full-width primary row. Phase 1 deliberately ships only the "From Computer" upload source and no cloud save destination — cloud/file-source variety returns in Phase 2 alongside the gateway API. The status counter still derives from `pendingCount`/`completedCount` (never raw `files.length`/`conversions.length`) so it stays accurate after deletions, new uploads, and TO changes; the Convert/Download buttons themselves are intentionally count-free so their width does not shift as the file list grows. State-based tinting: idle = white/slate-100 borders, processing = blue-50/40 bg + blue-100 borders + locked inputs, all-converted = emerald-50/30 bg + emerald-100 borders. `Regenerate all` no longer exists as a separate button; changing `Convert all to` re-runs every file via `handleConvert(true)` (forceAll). The conversion trigger after upload is now an explicit click on the inline `Convert` button — there is no auto-convert on file add because `handleConvert` reads `files` from closure and would race the `setFiles` update. The Convert button's `disabled` state is derived from `canConvert = files.length > 0 && pendingCount > 0 && !isProcessing` — it grays out the instant every file is converted (single file or many), and re-enables the moment a new file lands via `Add more files` or any per-file target change makes `pendingCount > 0`. The Download all button uses its own `canDownload` derivation (see DOX rule below).
- The file list section and the action area are now **layout-pinned**: the file list uses a conditional scroll — with 1-2 files the wrapper has `overflow-hidden` (no scrollbar track reserved, content shows at natural height) and switches to `max-h-[min(60vh,560px)] overflow-y-auto` only when `files.length > 2`. The action area is wrapped in `sticky bottom-0 z-20` so all three rows stay visible at the bottom of the browser viewport regardless of how many files are in the list. The sticky wrapper has a top border + upward shadow that visually separates it from the scrolling list. Do not change either height/scroll behavior without updating this contract.
- Transient CAD notices (zip progress, download success, download error) auto-dismiss via `flashCadNotice` after 7s for success / 10s for error. Successive notices reset the timer; the timeout is cleared on unmount.
